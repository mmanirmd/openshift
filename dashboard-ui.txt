## 3. Resource Selection and Search

At the top, provide these controls:

**Cluster**
- Select a single cluster.
- Support all configured clusters.
- Default to the currently selected cluster, if available.
- Do not hardcode cluster names.
- Handle unavailable clusters gracefully.

**Resource Type**
- Searchable dropdown populated dynamically using Kubernetes API discovery.
- Include standard Kubernetes resources, OpenShift resources, and CustomResourceDefinitions.
- Display resource Kind, plural name, and API group when necessary to avoid ambiguity.
- Example: Pods, Deployments, Routes, MachineConfigPools, SecurityContextConstraints, ClusterLogForwarders, Gatekeeper constraints.
- Support API group/version selection when required.

**Scope**
- Automatically detect whether the selected resource type is cluster-scoped or namespaced.
- Do not require the user to guess the scope.

**Namespace**
- For namespaced resources, allow selection of a namespace or All Namespaces.
- Disable or hide namespace selection for cluster-scoped resources.
- Populate namespaces from the selected cluster.

**Search**
- Search resource names.
- Support namespace filtering, label selectors, and supported field selectors.
- Add a clear/reset option.
- Validate selectors and show helpful error messages.
- Debounce free-text searches where appropriate.

**Important:** Do not fetch all resource types across all clusters when the page loads. Query only the selected resource type and cluster.

## 8. Read-Only Security Requirements

This is a critical requirement.

The Resource Explorer must never perform:
- Create
- Update
- Patch
- Delete
- Apply
- Scale
- Rollout restart
- Exec
- Port forwarding
- Other mutating operations

Enforce restrictions in both frontend and backend.

Use read-only Kubernetes RBAC with only the required permissions.

Do not grant cluster-admin to the Resource Explorer backend.

Do not assume that all resources are safe to expose simply because they can be read.

Implement a resource allowlist or explicit denylist policy that excludes sensitive resource types, including Secrets and sensitive custom resources.

Do not return raw sensitive resource data to the frontend before redaction.

Apply authorization checks to every endpoint, including YAML, Events, Logs, and Related Resources.

Ensure users cannot bypass restrictions by changing API parameters.

Audit resource access where appropriate.

If a resource is forbidden, return a clear permission-denied response.

## 9. Resource Search and Performance

The portal may manage clusters containing thousands of Kubernetes objects.

Optimize for performance:

- Query only the selected cluster and resource type.
- Use server-side label and field selectors where supported.
- Use Kubernetes pagination.
- Limit concurrent requests.
- Set API request timeouts.
- Cache discovery data.
- Avoid repeated expensive full-cluster scans.
- Cancel stale frontend requests when filters change.
- Debounce search input.
- Limit the size of YAML and logs returned.
- Avoid loading large datasets solely to calculate summary counts.

For generic resource types, distinguish exact server-side filtering from client-side filtering of the current page.

Do not present incomplete pagination results as a cluster-wide count.
