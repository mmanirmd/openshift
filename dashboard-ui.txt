## 6. Reserved IP address policy

For the existing /24 subnet convention, the first 40 addresses are reserved.

Example:

Subnet: 10.30.10.0/24

Reserved:

10.30.10.0 through 10.30.10.39

Available candidate range begins at:

10.30.10.40

Never allocate addresses from the reserved range.

The reserved range is intended for infrastructure and platform use.

Make this policy configurable per subnet.

Do not blindly apply the last-octet rule to arbitrary CIDR sizes. Use CIDR-aware calculations and explicit reserved address ranges.

Always exclude:
- Network addresses
- Broadcast addresses where applicable
- Configured gateway addresses
- Existing node IPs
- VIPs
- Existing infrastructure allocations
- Previously reserved addresses
- Other authoritative exclusions

Do not assume all free addresses form a continuous range.

## 7. Worker-node growth policy

The system must reserve capacity for **three times the initial worker-node count**.

This means:

Total worker capacity = Initial workers × 3

Future worker reservation = Initial workers × 2

Example:

Initial workers: 6

Future workers: 12

Total supported workers: 18

This is the required policy.

Do not interpret 3× as adding three times the original count.

### IP calculation example

New cluster:
- 3 control-plane nodes
- 6 initial workers
- 12 future workers
- 1 API VIP
- 1 Ingress VIP

Required addresses:

3 + 6 + 12 + 2 = 23

The dashboard must display:

- Initial workers: 6
- Future worker capacity: 12
- Total worker capacity: 18
- Total required IP addresses: 23

VIP allocation must be configurable according to the installation architecture. If VIPs are provided by an external load balancer or allocated from another subnet, do not double-count them.

If additional bootstrap or infrastructure IPs are required, include them explicitly in the calculation.

## 8. IP allocation algorithm

Implement the allocation engine in Python.

Use Python's standard `ipaddress` module.

The allocation engine must:

1. Parse the subnet.
2. Load authoritative existing allocations and reservations.
3. Apply infrastructure exclusions.
4. Calculate usable candidate addresses.
5. Determine required capacity.
6. Allocate IPs for control-plane nodes.
7. Allocate IPs for initial worker nodes.
8. Allocate VIPs when required.
9. Reserve additional IPs for future worker growth.
10. Return remaining capacity.

Prefer available addresses according to configurable allocation policy.

Do not require addresses to be contiguous if the subnet has gaps.

If insufficient capacity exists, show a clear error.

Example:

"Insufficient subnet capacity. Required: 23 addresses. Verified available: 18. Additional addresses needed: 5."

Never allocate the same address to two clusters.

Use database transactions, uniqueness constraints, and appropriate concurrency controls to prevent simultaneous users from reserving overlapping addresses.

Distinguish between:
- In Use
- Reserved — Infrastructure
- Reserved — Existing Cluster
- Proposed — New Cluster
- Reserved — Future Worker
- Available — Verified
- Unknown / Unverified

A preview is not a committed reservation.
