# Build Configuration Changes Dashboard — Platform Portal

Act as a senior Kubernetes platform engineer, Python FastAPI developer, and React/TypeScript frontend architect. Ignore anything that is not valid for exiting platform portal

**Your task:** Implement a new **Configuration Changes** page that helps platform engineers identify Kubernetes configuration changes over time, investigate changes, and compare before/after configurations.

Do not rebuild the existing application. First inspect the repository and reuse its routing, layout, styling, cluster registry, API client, authentication, and shared components.

## 1. Dashboard design

Create a clean, professional, enterprise-style dashboard consistent with the existing portal.

Visual preferences:
- Dark navy left navigation sidebar.
- Light main content background.
- White cards, subtle borders, blue accents.
- Green for successful/low-risk changes, amber for review, red for concerning changes.
- Spacious layout, not overcrowded.
- Responsive desktop-first design.

Add a **Configuration Changes** navigation item.

### Section A — Header and time filters

Title: Configuration Changes

Subtitle: Track configuration changes across Kubernetes clusters.

Provide:
- Time range: Last 24 hours, 7 days, 30 days, 90 days.
- Cluster: All clusters or individual cluster.
- Namespace: All or selected namespace.
- Resource type: All, Deployment, ConfigMap, NetworkPolicy, RBAC, Operator, etc.

Display four compact cards:
1. Total Changes
2. Clusters Affected
3. Changes Requiring Review

All values must come from actual backend data. Use loading, empty, unavailable, and error states. Do not hardcode demonstration counts in production.

### Section C — Configuration Change Timeline

Display a simple, readable time-series chart of changes across the selected period.

Support grouping by day and optionally by change category.

Do not overload the chart with too many series.

### Section D — Recent Configuration Changes

Create a searchable, sortable table with columns:

- Namespace
- Resource Type
- Resource Name

- Changed By
- Review Status

Examples of resources:
- Deployment
- StatefulSet

- NetworkPolicy

Provide pagination and filters.

Clicking a row should open a details drawer rather than navigate to another page.

### Section E — Change Details Drawer

Display:
- Cluster and platform
- Resource kind/name/namespace
- Change timestamp
- Operation type
- Actor, when known
- Source of evidence (audit log, watch event, GitOps, or snapshot comparison)
- Before and after configuration
- Field-level differences
- Related change ticket or Git commit, when available

Use a side-by-side or unified YAML diff viewer with added, removed, and modified lines.

Ignore noisy fields when comparing resources, such as:
- metadata.resourceVersion
- metadata.managedFields
- metadata.uid
- metadata.creationTimestamp
- status
- Other volatile system-generated fields where appropriate

Preserve security-relevant changes. Never hide a meaningful RBAC, NetworkPolicy, SCC, or security configuration change.

Never display Secret values, passwords, tokens, or private keys.

Add links to the existing Resource Explorer and Compare Clusters features when available.

## 2. Critical data collection requirements

Kubernetes does NOT provide a built-in historical database of resource changes covering 1, 7, 30, or 90 days.

Do not assume that listing current Kubernetes resources provides historical changes.

Design a reliable historical change collection architecture.

Support pluggable evidence sources:

1. Kubernetes API watches/informers for resource change detection.
2. Kubernetes or OpenShift audit logs for actor and operation information.
3. Periodic sanitized resource snapshots for before/after comparison.
4. Optional GitOps integration for Git commit and deployment correlation.

Explain the reliability limitations of each source.

Important:
- Watches identify observed state changes, but do not reliably identify the human actor.
- Audit logs can help identify actors, but availability, retention, and payload detail depend on platform configuration.
- GitOps commits show desired-state changes, which may differ from observed live-cluster changes.
- Historical data cannot be reconstructed if it was never collected.
- Deleted resources require prior snapshots or other retained evidence.
- Watch reconnects, expired resource versions, and collector downtime require recovery/reconciliation handling.

Use a persistent datastore for history. Inspect the existing project for a database before selecting a new one. 

Record:
- Unique event ID
- Cluster ID
- Provider
- API group/version/kind
- Namespace and resource name
- Resource UID where available
- Operation type
- Observed timestamp
- Audit timestamp where available
- Actor and actor source
- Evidence source
- Before snapshot reference
- After snapshot reference
- Normalized diff
- Collection confidence and completeness
- Correlation IDs or Git commit metadata where available

Deduplicate overlapping observations without incorrectly collapsing distinct updates.

Define retention and storage policies.

Use common Kubernetes APIs wherever possible.

Add optional provider adapters for platform-specific resources and audit integrations.

Do not hardcode OpenShift APIs into shared frontend components.

Use API discovery to identify supported resource types and capabilities.

If a cluster does not support a feature, show "Not available" rather than an error or fabricated value.

The frontend should receive normalized configuration change records regardless of platform.

Use UTC timestamps internally and format them in the UI according to user preferences.

Define typed Pydantic response models.

Avoid unbounded API queries.

## 5. Security requirements

The dashboard must be read-only.

Do not provide buttons to:
- Edit resources
- Apply YAML
- Roll back changes
- Delete resources
- Restart workloads

Use least-privilege Kubernetes RBAC for monitoring and collection.

Keep audit-log integration permissions separate from ordinary Kubernetes read permissions.

Sanitize configuration snapshots and diffs before storage and before returning API responses.

Do not persist Secret data, authentication credentials, or other sensitive configuration values.

Apply cluster-level and namespace-level authorization to historical records and API responses, including data collected before a user's access changed.

Record access to sensitive change investigations where required.

## 7. Implementation approach

Work in stages.

**Step 1:** Inspect the existing repository and explain which files and components can be reused.

**Step 2:** Propose the architecture, data model, and file changes. Clearly identify which data sources are available now versus which require new collectors or integrations.

**Step 3:** Implement the React dashboard with clearly labeled mock data only if real historical data is not yet available.

**Step 4:** Implement the FastAPI read endpoints and typed response models.

**Step 5:** Implement or scaffold the historical collector and persistence layer separately from the read-only portal API.

**Step 6:** Integrate with the existing multi-cluster registry and provider adapters.

**Step 7:** Add tests for filtering, pagination, change detection, diff normalization, secret redaction, and authorization.

**Step 8:** Provide setup instructions and a manual verification checklist.

## 8. Acceptance criteria

- Users can select 1, 7, 30, or 90 days.
- Users can view changes across multiple clusters.
- The UI identifies resource, cluster, timestamp, and change type.
- Actor information appears only when supported by evidence.
- Clicking a change opens a readable before/after diff.
- Sensitive values are never exposed.
- Historical data is clearly distinguished from current-state data.
- Missing history or unsupported integrations are shown transparently.
- Existing portal pages continue working.
- No cluster resources can be modified through this feature.
